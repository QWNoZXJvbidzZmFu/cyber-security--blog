网络渗透测试作业：笑脸漏洞检测PoC

1.漏洞原理

靶机 Metasploitable2 上装了一个 FTP 服务器 vsftpd v2.3.4（Very Secure FTP daemon）。2011 年 vsftpd 官方下载服务器被攻破，攻击者把 2.3.4 的源码包换成了带后门的版本——在 str.c 里多出一行与程序功能完全无关的代码。
后门的触发条件是：FTP 登录的用户名里包含一个“笑脸”：:)

字符 十六进制
: 0x3a
) 0x29

一旦匹配上，程序就调用 vsf_sysutil_extra()，开一个监听 6200 端口的 socket，把它的标准输入输出重定向到网络连接，再 execl("/bin/sh")。做用户名校验的是 vsftpd 的特权进程，它从绑定特权端口开始就一直以 root 运行（Metasploitable2 上 vsftpd 由 xinetd 拉起，进程本身也是 root），所以这个 shell 也就是 root。
多出来的代码只有 3 行，而且藏在 str_contains_space() 这个函数里——它本来是个合法函数，用来拒绝用户名里的空格。后门以 else if 的形式挂在空格检查的分支后面，扫一眼过去像是正常的边界处理：

漏洞编号 CVE-2011-2523，NVD 给的 CVSS v3.1 评分是 9.8（Critical）：AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H，弱点类型 CWE-78（OS 命令注入）。NVD 描述里明确写了受感染包的出现时间窗是 20110630–20110703，官方在 2.3.5 移除了这段代码。

2.检测思路

这次写的是 PoC ，分三步：

  1. 连目标 21 端口，依次发送 USER test:) 和 PASS，触发后门（只发 USER 不生效，原因见上一节）
  2. 尝试连目标 6200 端口
  3. 连上之后发一条 id，看能不能拿到回显

第 3 步是关键：光是 6200 端口能连上不足以证明这是后门 shell，万一那上面跑的是别的服务呢？必须拿到预期回显才算证据闭环。

这个”触发 → 连后门端口 → 执行固定命令 → 匹配特征输出”的四段结构不是我发明的，nmap 官方 NSE 脚本 ftp-vsftpd-backdoor 就是同一套逻辑，我的脚本相当于它的 Python 重写版。

0.环境：为什么靶机不是跑在 VMware 里

作业要求用 Metasploitable2，但我的电脑是 M1芯片。VMware Fusion 在 Apple Silicon 上只能虚拟同架构客户机，没有 x86 指令集模拟；而 Metasploitable2 是 2008 年的 32 位 x86 镜像，架构不匹配，连引导都做不到，这不是配置能解决的问题。能跑这种镜像的只有软件模拟（QEMU TCG），UTM 就是 QEMU 的图形壳。这里直接用 QEMU 命令行，好处是端口转发、抓屏、监控台都能脚本化。

有两个选择是刻意的：

  • 只绑 127.0.0.1。 带 root 后门的 FTP 一旦桥接进局域网，等于把整机 root 交给同网段任何人。镜像自己的登录横幅也写着 Warning: Never expose this VM to an untrusted network!。
  • FTP 走 2121 而不是 21。 macOS 上非 root 进程不能绑定 1024 以下端口，QEMU 会直接报 Could not set up host forwarding rule 'tcp:127.0.0.1:21-:21'。6200 和 22 不受影响，所以只有 FTP 需要换端口，由 PoC 的 --ftp-port 传进去。

🔥授权声明

所有操作只针对自己搭建的本地靶机。这个检测行为等同于发起一次真实攻击，对未授权目标执行属于违法行为。

另外补一句靶机内部的实际情况：Metasploitable2 的 vsftpd 不是 standalone 模式，/etc/vsftpd.conf 里是 listen=NO，21 端口由 xinetd 持有，每来一条 FTP 连接才拉起一个 vsftpd 进程：

这不影响漏洞本身（特权进程照样是 root），但解释了后面”重新触发”为什么能反复生效——每次触发都是一个新进程。

2.验证触发点：只发 USER 和发全 USER+PASS 的差别

第 1 节从源码推出”触发在 PASS 阶段的认证检查里”，这一步用靶机内部状态直接验证。方法是分别触发一次，然后在靶机里看 6200 有没有监听（内部命令走 SSH，127.0.0.1:2222，用户 msfadmin）：

发送内容 FTP 侧响应 靶机内部 sudo netstat -antp 里的 6200 行
只 USER test:) 331 Please specify the password. 无输出，6200 根本不存在
USER test:) + PASS 读超时（拿不到任何响应） tcp 0 0 0.0.0.0:6200 0.0.0.0:* LISTEN 5002/vsftpd
上一次后门还挂着时再触发一次 秒回 500 OOPS: priv_sock_get_result 仍是旧的那个监听，没有新进程

注意 netstat 里进程名还是 vsftpd：说明它此时停在 accept() 上，还没走到 execl。只发 USER 是打不出来的，这一点和我最初的写法相反。

3.运行 PoC，读取输出

  • FTP Banner: 220 (vsFTPd 2.3.4) —— 220 是 FTP 服务就绪码，括号里直接写了版本号，还没攻击就能判断目标是漏洞版本。
  • USER 响应: 331 Please specify the password. —— 331 表示用户名已收到。这一步后门还没触发，靶机里 6200 不存在（见上一节对照实验）。
  • PASS 响应: (无响应，超时) —— 这是成功的特征：特权进程执行完后门的 listen() + accept() 卡住了，认证结果永远回不来。反过来，如果这里几乎瞬间返回 500 OOPS: priv_sock_get_result，说明特权进程自己 exit(1) 了——bind(6200) 失败，端口还被上一次没退出的后门 shell 占着，这一轮是失败的（机制见本节第 4 小节的对照实验）。
  • 第 1/4 次发送 id，回显: uid=0(root) gid=0(root) —— id 的输出，uid=0 就是 root。
  • 退出码 0 表示确认存在，非 0 表示未确认，方便脚本化批量检测。

后门 shell 里能执行什么，单独试了一次（id、uname -a、cat /etc/issue.net、ls -l /root）：

/root 目录能列出来，就是整机 root，没有任何限制。

4.两个坑：后门只有一次机会，而且有冷却

坑一：一次触发只服务一个连接。 accept 拿到连接后紧接着 dup2 + execl("/bin/sh")，特权进程自己被 shell 替换掉了，那个 for(;;) accept() 循环随之不存在。谁先连上谁就把机会用掉了——nmap 的官方脚本为了确认真伪，自己就会去连一次。

实测：后门 shell 用完后，不重新触发直接连 6200：

在 QEMU 的用户态网络下，主机的 connect() 会先被 slirp 接住，所以失败表现是连上之后被 RST，而不是 Connection refused。判断”这次能不能用”不能只看能不能连上，必须看有没有回显——这也是 PoC 里 "uid=" in output 比”连接成功”更可靠的原因。

坑二：上一次的后门没退出，端口就一直是它的。 我一开始以为连续重试失败是 TIME_WAIT 造成的，做了对照实验才推翻自己。vsf_sysutil_extra() 在 accept 之后只 close(0/1/2)，监听 fd 并没有关，紧接着 execl("/bin/sh")——于是监听 socket 被 shell 继承下来，6200 继续 LISTEN，只是再也没人去 accept。

实验过程：触发一次，连上 6200 但不发命令也不断开，然后在靶机里看状态，再触发第二次。

对照下来判据很清楚：500 OOPS 秒回 = bind(6200) 失败，端口还被上一个后门 shell 占着，新特权进程走 exit(1) 分支（代码里没有 SO_REUSEADDR）；PASS 完全读不到响应 = 触发成功，特权进程卡在 accept() 上等着人连。Metasploit 模块里那句 Cooldown? 说的就是前者。

这条给检测代码两个直接结论：

  1. 看到 6200 开放并不等于能拿到 shell，必须发命令、看回显——这正是 PoC 里 "uid=" in output 比”连接成功”可靠的原因。
  2. 重试不能靠”立刻再来一次”。要么先把上一次的连接消费掉（发 exit 或断开并等进程退出），要么等端口释放。PoC 里两轮之间留 12 秒冷却就是干这件事的。

所以 PoC 的最终逻辑是：触发 → 等 2 秒 → 在同一条 6200 连接上反复发 id（慢速靶机从 bind 到 accept 有秒级延迟，连接先进 backlog，等对方开始 accept 时重发就有回显）→ 仍失败才重新触发，且两轮之间留 12 秒冷却。

5.靶机内部留证

客户机内部地址是 QEMU 用户态网段的 10.0.2.15，MAC 就是原镜像的 00:0c:29:fa:dd:2a——之所以要对齐 MAC，是因为 Ubuntu 的 udev 会按 MAC 固定网卡名，换了 MAC 就会被命名成 eth1，而 /etc/network/interfaces 里只写了 auto eth0，网络直接起不来。

5.成因与修复

成因分三层。直接原因是 str.c 里那段比对 0x3a 0x29 的代码，它和 FTP 的任何正常功能都无关。根本原因是源码分发渠道被攻破：用户从官方地址下载、按官方文档编译，每一步都没错，但缺少签名或哈希校验时，官方渠道一样能被掉包——“来源可信”不等于“内容可信”。放大原因是执行这段代码的是特权进程：vsftpd 的分离式设计里，负责认证的那个进程本来就是 root（Metasploitable2 上还叠加了 xinetd 以 root 拉起 vsftpd），于是派生出来的 shell 天然就是 root。

投毒是可复现验证的，不只是听说。 我把两份 2.3.4 源码都拉下来做了 diff：一份是发行版渠道的官方上游包，一份是带后门的 2.3.4 源码树。

两个文件里的时间戳正好落在 NVD 描述的 20110630–20110703 窗口内。同一个版本号 2.3.4，一份有后门一份没有，光看 vsftpd -v 或 banner 是分辨不出来的，只有哈希或 diff 能。这就是修复第 2 条存在的理由。

修复按优先级：

  1. 升级到 vsftpd 2.3.5 以上，官方已移除后门代码。
  2. 从官方渠道下载后校验签名或哈希再编译；有条件就用 apt、yum 安装，让发行版把关。
  3. 最小权限：绑定完特权端口就降权到普通用户，开启 chroot_local_user，用虚拟用户替代系统账号。这样即使再出现一个能执行命令的洞，拿到的也只是受限账号而不是整机 root。
  4. 网络层收敛：防火墙封掉 6200 这类非业务端口，FTP 限制来源 IP，有条件直接换 SFTP、FTPS 淘汰明文协议。
  5. 检测监控：netstat -antp | grep 6200 查异常监听；IDS 规则匹配形如 USER .*:\) 的用户名以及随后对 6200 的连接；定期用 OpenVAS 或 nmap NSE 漏扫。
